## 1. [P1] 최신 data_revision이 아닌 오래된 봉을 사용할 수 있음

**위치:** 대상 `load_local()` 299–320행. 관련 `market_schema.py` 41행, `parquet_store.py` 243–317행.

`DAILY_BAR_PK` 자체에 `data_revision`이 포함되어 있다. 따라서 `read_arrow(..., dedupe_pk=DAILY_BAR_PK)`는 같은 종목·날짜·세션·수정주가 유형이라도 리비전이 다르면 서로 다른 키로 남긴다. 저장소 내부에서 리비전 우선순위를 비교하더라도 리비전이 이미 키에 포함되어 있으므로 서로 다른 리비전끼리는 합쳐지지 않는다.

이후 `picked[(sid, d)]`는 REGULAR 봉을 처음 만나면 같은 날짜의 이후 행을 모두 건너뛴다. 이 단계에서는 리비전 정보를 읽어 선택하지 않는다. 예를 들어 revision 1의 REGULAR가 먼저 나오고 revision 2의 REGULAR가 나중에 나오면 revision 1이 유지된다. EXTENDED만 있는 날짜에서는 뒤에 나온 행으로 교체되지만, 이 역시 최신 리비전 순서라는 보장이 없다.

**영향:** 가격·거래량 수정본이 있어도 이전 값으로 이동평균과 패턴을 계산할 수 있다.

**수정 방향:** 원본 저장 PK는 유지하되, 조회용 논리 키 `(security_id, trading_date, price_scope, adjustment_type)`별로 `(data_revision, run_id)` 최대 행을 명시적으로 선택한 뒤 REGULAR 우선 정책을 적용한다. 최신 행이 FAILED일 때 제외할지 이전 정상본을 사용할지도 정책으로 정한다. 단순히 저장소 공통 PK를 변경하는 방식은 피한다.

**검증:** 동일 날짜의 revision 1·2를 입력 순서 양방향으로 주어도 같은 최신 봉을 선택해야 한다. REGULAR와 EXTENDED 혼합, 최신본 FAILED 조건도 별도로 검사한다.

## 2. [P1] C형에서 조정 구간 거래량이 모두 0이면 ZeroDivisionError

**위치:** `check_c()` 229–233행, `main()` 517행.

조정 기간 거래량이 모두 0이면 `volume_shrunk()`는 기준봉 거래량이 양수일 때 통과한다. 이어서 `seg_avg == 0`이 되고, 오늘 거래량이 0 이상이면 배수 하한 검사도 통과한다. 마지막 `today["volume"] / seg_avg`에서 예외가 발생한다. 종목별 평가 예외 처리가 없으므로 전체 스캔이 중단된다.

**재현 결과:** 실제 `evaluate()`를 합성 봉 30개에 호출하여 `ZeroDivisionError: division by zero` 확인.

- 앞선 20개 봉: 종가 100, 거래량 100.
- 기준봉: 시가 100, 종가 130, 거래량 1,000.
- 조정 8개 봉: 시가·종가 110, 거래량 0.
- 마지막 봉: 시가 110, 종가 115, 거래량 100.
- 각 봉의 `value`는 유동성 필터를 통과하도록 20억으로 설정했다. 이는 판정 함수의 산술 경계조건을 격리한 테스트이며 실제 시장 데이터 사례는 아니다.

**수정 방향:** `seg_avg <= 0`이면 C형 판정을 건너뛰고 사유를 남긴다. 공통 입력 검증에서 거래량·거래대금의 비정상 조합을 검사한다. 종목 단위 오류 격리도 추가하되 오류 종목 수와 원인을 보고서에 노출한다.

```python
seg_avg = sum(bars[k]["volume"] for k in seg) / len(seg)
if seg_avg <= 0:
    continue
```

`evaluate()`가 선택하지 않은 유형도 모두 계산하므로 `--types D`에서도 이 C형 예외가 실행을 중단시킬 수 있다.

## 3. [P1] 거래대금 정의가 데이터 소스에 따라 달라짐

**위치:** `load_local()` 319행, `load_kiwoom()` 339행, `check_d()` 237–256행, `evaluate()` 259–265행.

로컬은 `traded_value`가 있으면 실측값을 사용하고, 없으면 `close * volume`으로 대체한다. 키움 경로는 항상 `close * volume`을 사용한다. 확인한 `daily_scanner.kiwoom_daily_bars()` 반환 구조에는 거래대금 필드가 없다.

실제 거래대금은 거래별 가격×수량의 합이므로 종가×전체 거래량과 다르다. 예를 들어 거래량 100만 주, 거래량 가중 평균가격 9,000원, 종가 10,500원이면 실측 거래대금은 90억이지만 추정치는 105억이다. 다른 조건이 충족되면 D형의 100억 하한 통과 여부가 달라질 수 있다. 수정주가와 거래량의 조정 기준이 다르면 역사적 추정치의 일관성도 별도로 확인해야 한다.

**수정 방향:** `value_source` 또는 `value_is_estimated`를 저장하고 보고서에 표시한다. 실제 거래대금 확보가 가능하면 소스 간 정의와 단위를 통일한다. 불가능하면 추정치 허용 정책을 명시하고, 실측치와 추정치를 한 평균에 섞지 않거나 해당 종목을 별도 분류한다. 스키마도 공급자 미제공 거래대금을 null로 보존하도록 설명하고 있으므로, 스캐너의 추정은 별도 파생 필드로 관리하는 것이 명확하다.

**검증:** 실제 거래대금과 추정치가 임계값 양쪽에 놓이는 입력에서 판정과 표시가 정책대로 달라지는지 확인한다.

## 4. [P2] 중간 거래일 누락을 연속 조정일로 계산

**위치:** `check_a()` 156–177행, `check_b()` 180–202행, `check_c()` 205–234행, `main()` 504–508행.

최종 봉이 기준일과 같은지는 검사하지만, 그 사이의 거래일이 빠졌는지는 검사하지 않는다. B형의 4연속 음봉은 실제 날짜가 아니라 리스트상의 4개 행으로 판단한다. MA20과 신고가 기간도 같은 문제가 있다. 키움 로더는 OHLC 이상 봉을 제외하므로, 정상 수집 과정에서도 중간 날짜가 사라질 수 있다.

**영향:** 결측일을 건너뛴 4개 음봉을 4연속 음봉으로 오인하거나, 20거래일보다 긴 기간의 평균을 MA20으로 사용할 수 있다.

**수정 방향:** 기준 거래 캘린더와 종목별 날짜를 대조하고, 판정에 필요한 구간에 결측이 있으면 판정 불가로 분류한다. 휴장·거래정지·미수집을 구분하며, 달력 날짜가 하루씩 증가해야 한다는 검사는 사용하지 않는다.

## 5. [P2] 로컬 완료 봉 정책과 세션 혼용 관리 부족

**위치:** `load_local()` 288–325행, `load_kiwoom()` 330–335행, `main()` 510–515행.

키움 경로는 `include_incomplete=live`를 전달하지만 로컬 경로에는 미완료 당일 봉을 배제하는 검사가 없다. 로컬 저장소가 장중 봉을 포함할 수 있는 운영 방식이라면 `--live` 없이도 미완료 봉이 판정에 들어갈 수 있다. 실제 저장 파이프라인이 완료 봉만 쓰는지는 이번 검토에서 확인하지 않았다.

또한 EXTENDED 경고는 최근 22개 봉만 살핀다. D형 60일 신고가에는 그보다 오래된 봉이 사용되고, C형 기준봉의 직전 20일 평균 거래량도 최근 22개 범위를 넘는다. 오래된 EXTENDED 봉이 판정에 영향을 주어도 경고가 누락될 수 있다. 종목별 `extended` 값은 결과에 담지만 표에는 출력하지 않는다.

**수정 방향:** 소스 공통 완료 봉 정책을 두고, 실제 계산에 쓰인 전체 구간의 세션 혼용을 검사한다. 가능하면 동일 세션으로 계산한다. `--source local --live`는 지원 여부에 맞게 거부하거나 구현하고, 실제 적용된 상태만 표시한다.

## 7. [P2] --types 입력 검증 누락

**위치:** `main()` 461행 및 476행.

현재는 쉼표 구분 토큰을 파싱하지 않고 전체 문자열에 A/B/C/D 문자가 포함되는지만 확인한다.

| 입력 | 실제 파싱 결과 |
|---|---|
| `INVALID` | A, D |
| `A,Z` | A만 적용, Z는 무시 |
| 빈 문자열 | 유형 없음 |
| `A,B` | A, B |

위 결과는 실제 파싱 식을 실행해 확인했다. 잘못된 옵션으로도 정상 종료하거나 의도와 다른 결과를 만들 수 있다.

**수정 방향:** 쉼표로 분리하고 공백 제거·대문자 변환 후 각 토큰을 허용 목록과 대조한다. 빈 값·알 수 없는 유형은 `argparse.error()`로 처리한다. `--date` 형식 오류도 traceback 대신 명확한 CLI 오류로 반환한다.

## 8. [P2] 데이터 부족과 정상적인 후보 없음의 구분 부족

**위치:** `main()` 490–518행, `load_kiwoom()` 328–344행, `check_d()` 244–246행.

유니버스 일부만 수집돼도 그중 가장 최근 날짜를 전체 기준일로 선택한다. 종목 필터는 22개 봉 이상만 요구하지만, D형 60일 판정에는 60개 봉이 필요하다. 기간이 부족한 D형은 단순히 불일치로 처리된다. 모든 종목이 최종 필터에서 제외되어도 최초 calendar가 비어 있지 않았다면 빈 결과로 정상 종료할 수 있다.

키움 하위 함수도 토큰 확보 실패나 응답 부재에서 빈 결과 또는 수집된 일부 봉을 반환할 수 있어, 현재 출력만으로 미충족과 수집 실패를 충분히 구분하기 어렵다.

**수정 방향:** 미수집·기준일 불일치·기간 부족·품질 오류·유동성 미달·정상 불일치를 각각 집계한다. 유형별 평가 가능 종목 수를 표시하고, 데이터가 전부 제외되면 명시적인 실패 상태를 반환한다. 부분 수집에 대한 허용 기준도 정한다.

## 9. [P3] 추가 개선 및 설계 확인 사항

- **입력 계약:** 날짜 정렬·중복, 가격 양수, 유한값, OHLC 관계, 거래량 비음수 여부를 소스 공통으로 검증한다. 로컬 `quality_status != FAILED`는 PARTIAL도 허용하므로 품질 플래그별 허용 정책이 필요하다.
- **과거 조회 재현성:** `--date`는 현재 `index_stocks.json` 유니버스를 사용한다. 과거 시점 결과를 백테스트로 사용할 경우 당시 구성 종목, 데이터 가용 시각, 수정주가 기준일을 함께 관리해야 한다. 단순 과거 차트 조회와 당시 의사결정 재현을 구분한다.
- **시간대:** `date.today()`와 `datetime.now()`는 실행 PC 시간대에 의존한다. 다른 시간대 서버에 배포할 경우 Asia/Seoul 기준을 명시한다.
- **불필요한 계산:** 선택 유형만 평가하도록 개선할 수 있다. 다만 현재 ‘중복 유형’ 표시가 전체 유형 평가에 의존하므로 출력 정책을 함께 정한다. 거래량 리스트도 여러 번 만들기보다 한 번 계산해 전달할 수 있다.
- **WINDOW_TD:** 이름과 주석은 기준봉 탐색 창을 뜻하지만 실제로는 EXTENDED 경고에만 사용된다. 현재 A/B/C의 고정 탐색 범위가 22일 이내이므로 현 설정의 판정 오류는 아니다. 용도를 분리하거나 주석을 고친다.
- **설계와 버그 구분:** D형의 `>=`는 동일 최고가도 허용하며, B형 저가 조건은 MA20 아래로 깊게 내려갔다가 회복한 봉도 허용한다. A형은 전체 고저폭이 아니라 몸통 크기만 제한한다. 모두 현재 파일 상단 정의와 일치하므로 구현 버그로 단정하지 않는다. 더 엄격한 패턴이 필요하면 설계 변경으로 관리한다.

## 검증 결과와 권장 수정 순서

실행 확인한 항목은 Python 구문 컴파일 통과, 합성 데이터에서 C형 `ZeroDivisionError`, 유형 입력 파싱 결과다. 모듈의 `main()`은 실행하지 않았고, API 호출·실제 데이터 스캔·원본 보고서 생성은 하지 않았다.

1. 최신 리비전 선택과 C형 0 나누기를 먼저 수정하고 회귀 검증한다.
2. 거래대금의 실측/추정 구분과 소스 공통 입력 검증을 추가한다.
3. 거래일 연속성·완료 여부·세션 정책과 유형별 데이터 충분성 검사를 추가한다.
4. 보고서 실행별 보존, CLI 검증, 제외 사유 집계를 보강한다.

최소 회귀 검증에는 리비전 입력 순서 역전, 0 거래량 조정 구간, 거래대금 임계값 경계, 중간 거래일 누락, 59/60개 봉 D형 판정, 잘못된 CLI 옵션, 같은 날짜의 연속 보고서 저장을 포함하는 것이 좋다.

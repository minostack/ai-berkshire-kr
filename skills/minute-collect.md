# 분봉 일일 누적 (비어 있는 1분봉만 채우기)

> **봉 기준 `bars-1.0` (2026-10-03, `docs/BAR_STANDARD.md`)** — 일일 적재는
> 두 작업으로 한다 — 16:10 `data-load provisional`(밀린 날 확정 → 오늘 잠정 일봉)과 익일
> 08:30 `data-load daily`(1분봉 → 일봉 → 정규장 일봉 복원). 이 스킬은 **분봉만** 따로 채울 때 쓴다. 적재하는
> 분봉은 1분봉뿐이고, 5분·30분봉은 1분봉을 합성한다 — `period 5`는 과거 원본 재현용이다.

작업일 기준으로 **저장소에 비어 있는 1분봉만** 찾아 받습니다. "어제"를 기준으로
삼지 않으므로 **하루 이틀 늦게 돌려도, 연휴 뒤에 돌려도 빠진 날이 모두**
채워집니다. 같은 날 두 번 돌리면 두 번째는 받을 것이 없습니다(멱등).

**지원 입력 형식**:

```
/minute-collect                        # 최근 10거래일 확인 후 빠진 것만 수집
/minute-collect check                  # 무엇이 비어 있는지만 확인(수집 안 함)
/minute-collect days 20                # 확인 범위를 20거래일로
/minute-collect since 2026-09-01       # 특정 날짜 이후만
/minute-collect period 5               # 5분봉
/minute-collect recheck                # 영구 미달로 적어 둔 날까지 다시 받기
/minute-collect schedule               # 매일 자동 실행 등록 방법 안내
```

---

## 왜 `minute-cache build`가 아닌가

`build`는 종목마다 **API가 주는 끝까지** 받습니다. 매일 돌리면 같은 1년치를 매일
다시 받습니다 — 1분봉 350종목이면 하루 3천만 봉이 넘습니다.

`catchup`은 **무엇이 비어 있는지 먼저 확인하고, 그 구간만** 받습니다
(`fetch_security(min_date=…)`로 페이지 요청 자체를 줄입니다).

| | `build` | `catchup` |
|---|---|---|
| 받는 범위 | API가 주는 전 구간 | 가장 오래된 결측일까지만 |
| 매일 실행 | 같은 데이터를 매일 재수신 | 새로 생긴 하루만 |
| 늦게 실행 | 상관없음(전부 받음) | **빠진 날 전부를 스스로 찾음** |
| 용도 | 최초 구축·대량 보충 | **일일 누적** |

## 실행

```bash
# 기본 — 최근 10거래일을 확인하고 빠진 것만 수집
python cvdobv.py minute-cache catchup --period 1 --days 10

# 무엇이 비어 있는지만 확인(호출은 기준 종목 1개뿐)
python cvdobv.py minute-cache catchup --period 1 --days 10 --dry-run

# 범위 지정
python cvdobv.py minute-cache catchup --since 2026-09-01
python cvdobv.py minute-cache catchup --index KOSDAQ150
python cvdobv.py minute-cache catchup --codes 005930,000660

# 영구 미달로 적어 둔 날까지 다시 확인
python cvdobv.py minute-cache catchup --recheck

# 기준시각 고정(회귀 확인)
python cvdobv.py minute-cache catchup --as-of "2026-09-23 16:10"
```

## 매일 자동 실행 (Windows 작업 스케줄러)

2026-10-06부터 두 작업이 등록돼 있습니다(놓친 작업은 PC가 켜지면 바로 실행).

| 작업 | 시각 | 스크립트 | 하는 일 | 로그 |
|---|---|---|---|---|
| CVD 잠정 일봉 적재 | 월~금 16:10 | `scripts/provisional-load.bat` | 밀린 날 정규장 확정 → 오늘 1분봉 합 잠정 일봉(`data-load provisional`) | `logs/provisional-load/` |
| CVD 정규장 확정 적재 | 월~토 08:30 | `scripts/daily-load.bat` | 1분봉 → 일봉 → 정규장 복원(`data-load daily`) | `logs/daily-load/` |

확정을 **익일 08:30**에 두는 이유: 정규장 거래량은 "EXTENDED − 애프터마켓 분봉"으로
복원하므로 애프터마켓 확정(20:00 + 여유 5분) 뒤라야 합니다. 두 작업 모두 마지막 확정일
(`data/manifests/data_load_state.json`) 이후 밀린 날을 먼저 확정합니다.

예전 작업 "CVD 분봉 누적"(`minute-catchup.bat`, 16:10)이 등록돼 있으면 지웁니다:
`schtasks /delete /tn "CVD 분봉 누적" /f`

주말·휴장일에 돌아도 문제 없습니다 — 새로 받을 것이 없으면 그냥 끝납니다.
등록 확인은 `schtasks /query /tn "CVD 일일 적재"`, 즉시 실행은
`schtasks /run /tn "CVD 일일 적재"`.

> 스케줄러는 **에이전트 없이** 도는 경로입니다. 실패는 로그와 종료 코드로만
> 드러나므로, 주 1회 정도 `/minute-collect check`로 눈으로 확인하세요.

## 어떻게 판단하는가

### 1. 목표 거래일 — 캘린더가 아니라 API에서 얻는다

`silver.market_calendar`는 **수집한 일봉에서 파생**되므로 저장소보다 뒤처질 수
있습니다(실측 2026-09-27: 캘린더 최신 2026-09-22, 실제 마지막 거래일 **09-23**).
뒤처진 캘린더를 믿으면 빠진 날을 **애초에 목표로 삼지 못합니다.**

그래서 기준 종목(기본 삼성전자 005930) 분봉을 먼저 받아 **API가 실제로 주는
거래일**을 목표로 씁니다. 이 한 번의 호출이 캘린더 역할을 하고, 동시에 "API가
어디까지 과거를 주는가"(수집 지평)도 알려 줍니다.

### 2. 끝나지 않은 세션은 목표가 아니다

정규장이 끝나지 않은 당일을 목표에 넣으면 **반쪽 하루**가 저장되고, 다음 날에는
"이미 있다"고 판단해 영구히 반쪽으로 남습니다. 완료 판정은 V1.5
`is_session_complete()`를 그대로 씁니다.

### 3. 결측·부분 판정

`silver.bar_coverage`(정규장)와 대조합니다.

| 상태 | 기준 | 처리 |
|---|---|---|
| 결측 | 커버리지에 행이 없음 | 받는다 |
| 부분 | 봉 수 < 기대치 × **80%**(1분봉 기대 381봉 → 304봉) | 받는다 |
| 완전 | 그 이상 | 건너뛴다 |

`--min-completeness`로 기준을 바꿀 수 있습니다.

### 4. 영구 미달은 장부에 적고 건너뛴다

무체결·거래정지로 하루 봉이 원래 적은 종목은 매일 다시 받아도 늘지 않습니다.
받아 봤는데도 기준 미달이면 그 봉 수를 `data/manifests/minute_catchup_state.json`에
적고 다음 실행에서 건너뜁니다. **저장된 봉 수가 장부와 달라지면 다시
대상이 됩니다.** 장부는 지워도 안전합니다 — 다음 실행이 한 번 더 받아 볼 뿐입니다.

## 출력 읽기

```
분봉 일일 누적 — 1분봉 / 최근 5거래일 확인
  기준 종목 KRX:005930: 거래일 5일 확인 (API 최고(最古) 2026-09-04)
  대상 거래일 5일 × 종목 351개 → 결측 351쌍 / 부분 90쌍 (기대 381봉, 기준 80%)
    2026-09-17  결측   0 부분  34 완전 317
    2026-09-23  결측 351 부분   0 완전   0
  수집: 351종목, 20260917 이후, 페이지 상한 8
```

수집 후에는 **재확인 결과**가 붙습니다.

```
완료: 7,159봉 저장, 목표 22쌍 중 메워진 (종목,일) 0쌍, 5.2초
  ⚠ 미해결 덜 받음 또는 무체결: 22쌍
```

`목표 N쌍 중 메워진 M쌍`은 **이번에 목표로 잡은 (종목, 날짜)에 한해서만**
셉니다 — 계획과 재확인을 다른 집합에서 세면 복구 수가 음수로 나옵니다
(실측 2026-09-27에 `-67쌍`이 나와 고쳤고,
`tests/unit/test_minute_catchup.py::test_복구_집계는_목표로_잡은_쌍만_센다`가
회귀로 고정합니다).

남은 구간은 이유별로 분류합니다.

| 분류 | 뜻 | 복구 |
|---|---|---|
| `BEFORE_API_HORIZON` | API가 그 날짜를 더 이상 주지 않음 | **불가** |
| `NO_DATA` | 응답에 그 거래일이 없음(상장 전·거래정지·폐지) | 불가 |
| `STILL_PARTIAL` | 받았는데도 기준 미달(무체결 가능성) | 장부에 적고 다음부터 건너뜀 |

> `STILL_PARTIAL`은 "수집 실패"와 "그날 거래가 적었다"를 **이 데이터만으로는
> 구분할 수 없습니다.** 그래서 지우지 않고 세어 보고합니다.

## 대상 종목

`--index`(기본 `KOSPI200,KOSDAQ150`)의 **목표 거래일 구성종목 합집합**입니다.
유니버스 이력(`silver.universe_membership`)을 먼저 보고, 이력이 그 날짜를 덮지
못하면(당일 편입분 등) `data/index_stocks.json`으로 보완합니다. 어느 쪽에서
왔는지는 결과 JSON의 `member_sources`에 남습니다.

구성종목이 바뀌면 **새로 들어온 종목은 과거 분봉이 아예 없습니다.** 이때
`--days`를 늘려 잡으면 그만큼 과거를 받습니다(API 지평까지만).

## 종료 코드

| 코드 | 뜻 |
|---|---|
| 0 | 정상 — 빠진 것을 모두 채웠거나 채울 것이 없었다 |
| 9 | 부분 성공 — 미해결 구간이 남았다(무체결·지평 밖 포함) |
| 4 | 데이터 품질 실패 — 한 봉도 저장하지 못했다 |
| 5 | API 실패(토큰·네트워크) |

배치 스크립트는 **9를 실패로 취급하지 않습니다** — 무체결·거래정지가 정상적으로
섞이기 때문입니다.

## 주의사항

1. **1분봉은 무겁습니다.** 350종목 × 5거래일이면 약 100만 봉, 10분 내외입니다
   (초당 5회 제한). `--days`를 크게 잡으면 그만큼 늘어납니다
2. **API 지평 밖은 복구할 수 없습니다.** 실측상 ka10080은 요청 시점에서 과거
   일정 구간까지만 줍니다 — 오래 방치하면 그 구간은 영구 손실입니다.
   **이 스킬을 매일 돌리는 이유가 그것입니다**
3. 애프터마켓·시간외 봉도 함께 저장되지만 **완전성 판정은 정규장 기준**입니다
   (CVD 흐름 계산이 정규장만 쓰기 때문)
4. `--period`를 바꾸면 **다른 데이터셋**입니다(저장소에 주기별로 공존).
   1분봉과 5분봉의 커버리지·장부는 서로 독립입니다
5. 수집이 끝나면 `/cvd-accel-scan`이 그 데이터를 씁니다 — 순서를 지키세요
6. 1분봉은 **정규장 일봉 복원**에도 쓰입니다(`cvdobv.py daily-cache
   regular-from-minute`, `/ab-candidate-scan` 3단계). 애프터마켓 봉이 완결돼야
   하므로 **20:00 확정 전에 받은 날은 복원하지 않습니다**(수집 시각은 `run_id`로
   판정). catchup은 **애프터마켓 확정 전에 받았고 지금은 확정이 지난 날**을 정규장이
   완전해도 다시 받습니다(출력의 `애프터마켓 미확정 N쌍`). 16:10 실행이면 오늘 받은
   정규장 분봉은 내일 16:10 실행에서 애프터마켓까지 다시 받혀 복원 대상이 됩니다
